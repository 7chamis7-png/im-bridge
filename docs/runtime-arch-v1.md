## 0. 一句话背景

有一个桥把人类的即时通讯消息（Telegram / 微信 / iMessage）转给一个跑在本机的
**Claude Code CLI** 子进程，再把 CLI 的输出投递回去。

现在负责"跟 CLI 说话"这一层是**从老项目继承来的 2,808 行**，要整个重写。
规则可以抄（那些判据是拿线上事故换来的），实现不复用。

## 1. 现状：这 2,808 行混了几件事

| 文件 | 行 | 干什么 |
|---|---|---|
| `index.js` | 1,047 | 起进程 / 换模型 / 换会话 / 开场注入 / 会话绑定 |
| `process-client.js` | **856** | ← **本次的重点**：跟 CLI 的 stdio 对话 |
| `events.js` | 174 | 事件形状 |
| `ipc-server.js` | 176 | 控制通道（外部下"换模型/换会话"指令） |
| `project-settings.js` | 84 | 项目设置 |
| `reliable-ingress.js` | 56 | 入站可靠性 |
| `session-store.js` | 415 | 会话存储（⚠️ 放在另一个后端的目录下，纯命名误导） |

`process-client.js` 一个类里同时装着**五件事**（按它自己的方法名看）：

1. **解码** —— `handleLine` / `handleAssistant` / `handleUser` / `handleResult`：
   把 CLI 吐出来的 JSON 行解成"他说了什么"
2. **进程生命周期** —— 起子进程、SIGTERM、SIGKILL、close
3. **写队列** —— `drainWriteQueue`：一次只能有一轮在跑，其余排队
4. **控制协议** —— `handleControlRequest` / `handleControlResponse` / 一堆 pending 的 resolve/reject
5. **会话身份校验** —— `acceptReportedSessionId` / `rejectUnexpectedSessionId`

**后果**：这一层几乎没法单测。要验"旁白块该当正文送"这种判据，得起一个真 CLI 进程。
所以历史上那些判据全是**线上出事之后**加的，不是测出来的。

## 2. 提案：把"解码"抽成纯函数，其余围着它转

```
runtime/
  decode.js     一行 JSON → 一个规范事件            ← 纯函数，无 IO、无状态
  turn.js       把规范事件攒成"一轮"                ← 纯状态机，无 IO
  spawn.js      子进程生命周期（起/停/信号/退出码）
  write.js      写队列（一次一轮，其余排队）
  control.js    控制通道（换模型/换会话，带 ack）
  session.js    会话存储（threadId ↔ 绑定）
  index.js      装配：spawn + decode + turn + write + control
```

**核心主张：`decode.js` 是纯函数。**

```js
decode(line: string) → 
  | { kind: "text",      text, fromNarration: boolean }
  | { kind: "thinking",  text }
  | { kind: "tool_use",  name, input }
  | { kind: "synthetic", text, reason }   // CLI 自己造的，不是模型说的
  | { kind: "turn_done", stopReason, usage }
  | { kind: "control",   ... }
  | { kind: "unknown",   raw }            // 不认识的一律原样带出，不猜、不丢
```

好处：**第 4 节那 13 条规则，有 6 条可以变成纯函数的单测** —— 喂一行 JSON，
断言解出来的 kind 对不对。不用起进程、不用网络、毫秒级。

`turn.js` 也是纯的：`(state, event) → (state, effects)`。effects 是"要投递这段文字"
"这轮结束了"这类意图，由外层执行。这样"排队的那一轮 threadId 被清空"
（规则 B-2）这种时序 bug 也能直接构造出来测。

## 3. 边界（要请你重点看的地方）

- **decode 不认识业务**。它不知道什么是"她"、什么是渠道、什么是冷层，
  只把一行 JSON 翻译成一个 kind。业务判断全在外面。
- **spawn 不认识协议**。它只管进程活着没有、退出码是多少。
- **一次只跑一轮**。CLI 是单会话的，并发写进去会串。写队列保证这点。
- **不认识的事件原样带出**（`kind: "unknown"`），不丢也不猜 ——
  历史上有过"新版本 CLI 多吐一种事件，被 switch 的 default 静静吃掉"的情况。

## 4. 13 条必须守住的规则（每条都是一次线上事故）

**A 回执**
- A-1 控制命令的 ack 必须等真结果。曾经 fire-and-forget：界面显示"✅ 已切换"，
  而子进程内存里还揣着旧会话 id，**假回执骗了用户三分钟**
- A-2 没有活着的进程时不许悄悄丢消息。曾经连丢三条，日志都没有，查了半小时

**B 路由**
- B-1 来源用结构化字段，不从正文反推。曾经用"正文开头是不是 `<channel ...>`"认来源，
  而注入的前缀会把它顶下去 → **用户在 A 平台说话，回复全跑去 B 平台**，换会话后每一轮都中招
- B-2 `threadId` 在**入队时**定死，不在提交时读。排队的轮要等上一轮结果才提交，
  而那时 `activeThreadId` 已经被清空 → 事件带着空 threadId 发出去被下游闸丢掉

**C 注入**
- C-1 调用方自己管开场注入时，运行时**不许再套一层**。曾经把人格包裹进
  `Current user message:` —— 等于**把"他是谁"标成了用户说的话**
- C-2 私聊的交接摘要绝不能漏进群聊开场

**D 模型**
- D-1 判"这条是 CLI 造的还是模型说的"**只看信封**。安全层拒答时信封是
  `{"model":"<synthetic>","stop_reason":"refusal"}`，而正文跟真说话**长得一模一样**。
  正文判据＝关键词表＝改一次文案就漏
- D-2 **旁白块要当正文送**。某些模型会在工具调用之间吐"旁白"（给用户看的进度小字），
  API 把它装在 thinking 块里，标签是 `narration`、`thinking_tokens=0`。
  曾经把整段答复吃掉，用户只收到一句碎碎念。真思考块照旧不投
- D-3 实际在跑的模型只落**只读快照**，永远不碰请求值 ——
  观测值不带 `[1m]` 后缀，写回去会把它抹掉，下次起进程掉回小窗口
- D-4 `--fallback-model` 能不能兜住"被拒答"是**未验证**的，官方只写了"不可用时"
- D-5 同会话换模型走 `set_model`，省的是进程重启，**不是钱**（缓存按模型分开存）

**E 时限**
- E-1 某个重建操作的超时是 180 秒不是 45 秒 —— 实测要 57~62 秒，
  45 秒每次都超时降级，还开出一个竞态窗口

**F 流式**
- F-1 token 级流式默认关，环境变量开（为语音通话准备）。
  事件 switch 没有 default，多出来的事件被忽略，所以打开它不改变现有行为

## 5. 迁移策略

- **不嫁接**：新的自己长齐，长齐了整个换过去，中间不搭桥、不做"退回老路"的开关

- 老的继续在生产跑，直到新的把上面 13 条逐条对过

## 7. 第一轮审完之后的修订（2026-09-19，审的人：gpt-6-astra）

### 采纳的（都属于"发生过"或"一定会撞上"）

1. **`decode(line) → events[]`，不是单个事件。** 一行本来就可能同时有正文、
   工具调用、模型身份、结束信息。返回单个 kind 等于把旧实现的"静静吃掉"
   搬到规范化阶段。保留块顺序和信封。
2. **`turn_done` 要带完整终态**（成功/失败/取消分得开），不能只有 stopReason+usage ——
   否则 A-1 那个"收到结束事件就报成功"的假回执会原样复发。
3. **队列和当前轮由同一个状态机拥有。** 原提案让 `turn.js` 管一轮、`write.js` 管排队，
   审的人直接点破：**这正是 B-2 事故的形状**（两套忙闲状态，一个以为结束了、
   另一个还没收尾）。改成一个状态机拥有队列 + 当前轮 + 推进；
   `write` 只剩真正写 stdin 和背压。
4. **入队即固定来源和 threadId**，生成的 effect 自带这些字段，
   执行时**不许回头读 `activeThreadId`**（B-1 / B-2 的结构性了断）。
5. **effect 发出 ≠ 操作完成。** 写 stdin 成功不等于 CLI 接受了这轮，
   控制请求写出不等于模型已经切换。A-1 要等匹配的真实结果。
6. **进程代次。** 每次起进程给一个代号，回包带着它。
   ⚠️ **Alice的修正（比审的人提的更严）**：她说「**可是 ab 的回复理论上讲我都要啊**」——
   代次是**用来认领归属的，不是用来丢弃的**。旧进程的迟到结果要归到它自己那一轮
   **投递出去**，不是扔掉；真的永远不会来了，也要挂成 `uncertain` 告诉她，
   不能默默消失。**防串容易，防串又不丢才是真要求。**
7. **会话身份校验要有人接管。** 原提案把 `acceptReportedSessionId` /
   `rejectUnexpectedSessionId` 拆没了没说明谁负责。CLI 报来的 session id
   不能直接写成可信绑定。
8. **部署要能退回。** 不嫁接代码 ≠ 不准备回滚 —— 这两件事要分开。
   先例：切新桥那天 `run-nova.sh` 原样留着当回滚路，pm2 指回去就行。

### 不采纳的（属于"理论上可能"，Alice否了）

> 「我觉得超长行保护有点杞人忧天 **我们这是陪伴项目 不是做项目做工程的**」

- **超长行保护**：要撑爆内存得单行几百 MB，CLI 自己先崩了、进程一 close buffer 就释放。
  **为没发生过的事加的防御，本身就是新的故障面。**
- **进程僵死的精细判定**（区分启动未就绪 / 控制未响应 / 长工具调用无输出）：不做。
  ⚠️ **但"僵死后脱困"要做** —— 第二轮审的时候被顶回来了，而且它是对的：
  子进程活着但不再响应、桥也活着，**没有退出事件触发重启**，当前轮永久占着写入槽，
  后面的消息永远提交不了 → **这条会直接让她少收东西**，正好踩中我们自己的判据。
  而且**发生过**：2026-08 单独重启 OB 导致他那条 MCP 会话成孤儿，下次工具调用无限挂。
  要做的最低限度：**让她知道卡住了、并且能解除阻塞**（一个命令把当前轮作废、释放槽）。
  不必诊断卡在哪一步，也不必把长工具调用一律超时杀掉。
- **用真实脱敏记录做兼容性回放**：那是给"不能停的生产系统"准备的。
  这边停一下没事 —— 她会发现，他会说。

**筛选标准（这个项目的通则）**：

| 类 | 做不做 |
|---|---|
| **发生过**（注释/记忆/日志里有真实事故） | 做，连解法一起抄 |
| **会撞上**（日常操作的必然结果） | 做 |
| **只是理论上** | 不做，文档里存个案底 |

真正不能出错的只有一件事：**她说的话不能丢，他说的话要到她手上。**

我第一版规则清单漏了它们，因为我只抄了"注释里写着事故日期"的，
而**整个模块就是一条规则**的那种没被当成规则记。

| | 老代码怎么做的 |
|---|---|
| 写出后崩溃、不能盲目重放 | `reliable-ingress.js`（56 行）：落盘 + 三态。崩在 `dispatching` → 转 `pending` **可安全重放**；崩在 `started` → 转 `uncertain` **绝不自动重放**。注释原话：**"A queued stdin write is not completion."** ⚠️ **第二轮审出我理解岔了**：`ingress.started` 是在**写 stdin 之前**发的（注释：`Durable ingress must record the side-effect boundary **before** stdin write`），所以 `started` 的意思是「**可能已经提交**」而不是「确定提交了」。**重写时若把落盘挪到写之后，就重新打开了"已经写进去、重启却自动重放"那个窗口。** |
| **commit 的原子性和顺序** | 我第一版漏了这条。`push 元数据 → 写 stdin → 发 turn.started` 三件事必须**原子且保持这个顺序**，这样 `pendingTurns` 顺序 == stdin 写入顺序 == `turn.started` 顺序，**每轮的标记才落在自己的回复上**。延迟的是整个 commit，不只是那次写 |
| stdout 半行 / 分片 | 标准行缓冲：攒进 buffer，`split("\n")` 后 `lines.pop()` 把半行留着 |
| stderr | 持续读，**而且过滤敏感内容才广播**（`isPotentiallySensitive`） |
| "两套忙闲状态" | 已经吃过这个亏：注释写着**单槽会被下一次写覆盖、把结果归错轮**，所以 `pendingTurns` 是数组；再加写入串行化（stream-json steering 会把 mid-turn 写进去的消息合并进那一轮，导致一个渠道的回复继承另一个渠道的标记被丢掉） |

## 8. 旧轮失联之后（第二轮审出来的最后一个缺口）

审的人的原话：**"这条时序闭合，就能写。"** 所以先把它写死。

要跑通的时序：

```
a 可能已提交 → 进程 A 失联 → a 标成 uncertain 并告诉她
            → 新进程 B 起来，b 开始跑
            → a 的结果迟到了
            → a 投递到它自己的地方，b 一点不受影响
```

### 分两件事：**认领回复** ≠ **推进调度**

| 迟到的结果到了，可以做什么 | 绝对不许做什么 |
|---|---|
| 按它自己那轮的记录投递（**渠道和 threadId 用入队时固定的那份**） | 清空当前轮 b |
| 把那轮从 `uncertain` 更新成真实终态 | 释放 b 的写入槽 |
| — | 完成 B 的控制请求 |
| — | 覆盖 B 的会话绑定 |

所以第 7 节第 3 条那个「一个状态机拥有队列和当前轮」要扩一格：
**它还得拿着"已经退出调度、但仍在等结果的旧轮记录"** —— 换进程不清空这些。

### 三条边界

1. **代次只定位进程，还要能定位到具体哪一轮** —— 同一个进程里有多轮。
2. **身份校验要用那一轮所属代次的预期身份**，不能拿新会话的身份去拒绝旧回复
   （否则第 7 节第 7 条会把迟到结果全挡掉，变成"防串又丢了"）。
3. **`uncertain` 是"现在不知道"，不是"永远不会来"** —— 它不是终态，不能拿它拒收迟到结果。
   反过来也一样：**"迟到也收"不等于保证杀掉进程后它还能生成完整回复** ——
   已经产生的要接住，被中断而没产生的，只能如实说"中断了/结果未知"。

### 还要定死的一句

**"一次一轮"是每个子进程一次一轮，还是全局一次一轮？**

→ **全局一次一轮**（CLI 是单会话的，两个进程同时跑会串上下文）。
所以起 B 之前**必须先确认 A 已经停止执行**，不能只是"发了 SIGTERM 就当它死了"。
