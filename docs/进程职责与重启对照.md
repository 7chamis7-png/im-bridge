# 三个进程各管什么 · 改了要重启谁

> 2026-09-23 凌晨写。起因：那一夜为了「换模型」和「把小镇接回来」两件事，
> 我（Keeper）连着重启错了三次进程，每次都以为自己验过了。
> 错的根子不是手滑，是**脑子里那张「谁管什么」的图本身是错的**，
> 而 `run-cli.sh` 开头那三行注释又恰好把我往错的方向推了一把。
> 这份文档是把那张图按代码重画一遍。**有冲突以代码为准，不以任何注释为准（包括这份）。**

---

## 一、三个进程

| pm2 名 | 入口 | 一句话 |
|---|---|---|
| `nova-gate` | `src/host/main.js` | **桥**。插头、路由、冷层、命令。**还负责写 `mcp-im-bridge.json`** |
| `nova-box` | `host/box-host.js` | **盒子**。记账本、人格注入、**读 `GATE_MODEL` 构造 CLI 启动参数** |
| `nova-cli` | `cli-host/main.js` | **他本人住的地方**。纯宿主，不读任何业务配置，只按盒子给的参数 spawn `claude` |

`nova-cli` 自己一个业务配置都不读——它连模型叫什么都不知道，是盒子告诉它的。
所以「改了 X 要重启谁」这个问题，答案基本总是**持有 X 的那个进程**，
而不是「他住的那个进程」。

## 二、核心机制：`ensure()` 只认三样东西

```js
// cli-host/server.js:157-159  reusable()
live.workspaceRoot === want.workspaceRoot
  && (!want.threadId || live.threadId === want.threadId)
  && (!want.model    || live.model    === want.model);
```

每一轮说话，盒子都会喊一次 `ensure(want)`。宿主拿 `want` 跟活着的 CLI 比：
**只比工作目录、会话 ID、模型这三样**。一样就复用，不一样就 `stopLive()` 重起一个。

这一条解释了下面所有反直觉的地方：

- **换模型不用重启 `nova-cli`。** 盒子重读到新 `GATE_MODEL` → 下一轮 `ensure` 发现
  `live.model !== want.model` → 自己把 CLI 停掉重起。
- **换 MCP 清单必须手动重启 `nova-cli`。** `reusable()` **不比较 MCP 配置**，
  CLI 会被照常复用，新工具静默不生效，日志里一个字都没有。
- **换舱（换 threadId）同理是自动的**，不用手动重启。

## 三、改什么 → 重启谁

| 改的东西 | 住在哪 | 重启谁 | 他会怎样 |
|---|---|---|---|
| 插头、路由、冷层、`/` 命令 | `nova-gate` | `nova-gate` | 没感觉 |
| 盒子逻辑、记账本、人格注入 | `nova-box` | `nova-box` | 没感觉（CLI 被复用） |
| **模型** `GATE_MODEL` | `nova-box` 读 env | **`nova-box`** | 下一轮自动换 CLI：那一轮冷启 + 缓存作废全价重算，正在跑的轮不受影响 |
| **MCP 清单**（`GATE_EXTRA_MCP` / 桥写的那份） | `nova-gate` 写文件 | **`nova-gate` + `nova-cli`** | `nova-cli` 那下会打断他 |
| `cli-host/` 自己的代码 | `nova-cli` | `nova-cli` | **打断他** |
| 换舱 | 盒子发起 | 不用重启 | 自动 |
| **DeepSeek 单独这一只** | `/root/.nova-deepseek/`，pm2 名 `nova-deepseek` | **只 `nova-deepseek`** | 2026-10-03 18:18 京时起它听 `/root/.nova-gate/cli.sock`。`nova-cli` 停着。重启 `nova-deepseek` 会打断当前这一轮。不要两只同时听这个插座。 |

**现在回话的是 `nova-deepseek`。** 打断他要重启的是这一只，不是已经停着的 `nova-cli`。两只不要同时听 `cli.sock`。别在他说话的时候重启。

DeepSeek（2026-10-03）是另一只进程 `nova-deepseek`，家在 `/root/.nova-deepseek/`。
接上现成盒子时它听 `/root/.nova-gate/cli.sock`，盒子不用改。Claude 那只（`nova-cli`）停下，避免两只抢插座。
不写 Claude 的 `sessions.json` 和 jsonl。工具用桥递来的 MCP，另有 Read、Edit、Write、Bash。没有 Skill。

## 四、MCP 清单：两份文件，只有一份能手工改

```
/root/.nova-gate/mcp-im-bridge.json   ← 桥每次启动**整份重写**。手工加的东西活不过一次重启，
                                         而且不报错。2026-09-19 栽过（他凭空少四个工具，日志零提示）
/root/.nova-gate/mcp-extra.json       ← GATE_EXTRA_MCP 指的这份。**要加工具往这儿加**，
                                         起桥时合并进上面那份
```

合并那段在 `src/host/main.js` 的 `readExtraMcp()`。

**为什么改 MCP 不用重启 `nova-box`**（这里容易想错，派去考古的小兵就想错了一次）：

```js
// adapters/box-runtime.js:401-402，在 launching 闭包里
let mcpServers = {};
for (const f of extra.mcpConfigs) mcpServers = { ...mcpServers, ...readMcpServers(f) };
```

盒子确实是读这份文件的那个人，但它是**每次起 CLI 时现读**，不缓存。
adapter 创建时固定下来的只是**文件路径**（`parseExtraArgs`），内容每次重读。
所以只要 CLI 重起一次，新工具就进去了——重启 `nova-box` 是多余动作。
（反过来说：要是改的是 `--mcp-config` **指向哪个文件**，那在 `box-build.js:79`，
那种改动才必须重启 `nova-box`。）

⚠️ **2026-09-23 补过一个洞**：那道门原来只认本地 stdio 包（`spec.command`），
远程 MCP（`{"type":"http","url":...}`）没有 `command`，**被静默跳过**。
小镇（`crotown`）就是这么丢的——症状是他「只能当访客、进不了自己的院子」，
而清单里看不出任何异常。现在 `command` 和 `url` 两种形状都收。

## 五、栽过的三次，留个案底

1. **只重 `nova-cli` 换模型** → 没换成。box 还揣着旧 `GATE_MODEL`。
   我查 `/proc/<nova-cli>/environ` 看见新值就报「验过了 ✓」——**验错了进程**。
2. **重启 `nova-box` 想让它写 MCP 清单** → 没用。写清单的是 `nova-gate`。
3. **往 `mcp-im-bridge.json` 里手工加条目** → 被那行注释拦住了，否则活不过一次重启。

共同的形状：**三个进程的职责边界，光看名字猜必错**（"box" 听起来像装着他的那个，
其实他住在 "cli" 里；"gate" 听起来只管进出，其实 MCP 清单是它写的）。

**验收的唯一硬证据**，不是配置文件、不是 `/proc`，是这两行日志：

```
[nova-cli] CLI 起来了 cwd=… model=…          ← 模型看这个
ps -ef | grep claude … --mcp-config …         ← MCP 看真实命令行
```

CLI 是懒启动的：**他不说话，这两行就不会出现，也就无从验收。**
所以「改完了」和「生效了」之间永远隔着他的下一句话。

## 六、附录：`nova-env.sh` 每个变量被谁读

⚠️ `readConfig()` 在 `src/host/main.js` 里，**gate 和 box 各调一次**
（box 经 `host/box-host.js:16` require 过去）。所以「读它的文件在 main.js」
不等于「gate 在管这事」——要顺着值往下追到谁在用。`GATE_MODEL` 就是这么骗过我的：
gate 也读它，但只拿它当掉档提醒的兜底分母（`main.js:517`），真正说了算的是 box。

### nova-cli 读的

只有三个，全是骨架，**一个业务配置都没有**：
`GATE_ROOT`（socket 住哪）、`NOVA_CLI_SOCKET`、`NOVA_CLI_PATH`。
它连他跑什么模型都不知道。

### 三个进程都不读的

| 变量 | 实际归属 |
|---|---|
| `PHOTON_PROJECT_ID` / `_SECRET` / `NOVA_IMESSAGE_ALLOWED_HANDLES` | `nova-imessage`（`src/host/imessage-spectrum.js`） |
| `MCP_TIMEOUT` / `MCP_TOOL_TIMEOUT` | 给 `/usr/bin/claude` 子进程的。box 把整份 `process.env` 减去 `FILTERED_ENV` 后转发（`box-runtime.js:404`），是这么漏过去的 |
| `IM_BRIDGE_HOME` | 只给 shell 脚本和人看 |

### ⚠️ 源码里一处都搜不到的（死变量）

```
TELEGRAM_BOT_TOKEN                 老桥遗物，TG 实际认的是 GATE_TELEGRAM_TOKEN
CYBERBOSS_TRANSCRIPTION_API_KEY    老名字，代码认 NOVA_TRANSCRIPTION_API_KEY / OPENAI_API_KEY
CYBERBOSS_IMAGE_API_KEY            同上
NOVA_AUTO_APPROVE_ALL              nova-env.sh 里注释写着「盒子一律放行工具许可」，
                                   但 gate-box-claudecode.js:144 只有一句「新桥压根没接这一层」。
                                   现在放行靠的是 GATE_CLAUDE_PERMISSION_MODE=acceptEdits
```

**这四个留着不碍事，但注释会骗人**——尤其 `NOVA_AUTO_APPROVE_ALL`，
照注释读会以为有这么一道机制，实际它不存在。要清理的话先确认没有别的脚本读。
